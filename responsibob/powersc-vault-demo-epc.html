Recommendations — ordered by energy impact

🔴 Medium impact — Algorithm axis improvement
Replace 150 sequential curl calls with a single Vault batch-issue request
replace-with-vault-certificates.sh issues 150 certificates via 150 individual curl calls — each one is a complete TCP + TLS + HTTP round-trip. Vault's PKI engine does not natively issue N certificates in a single call, but the pattern can be restructured: generate a pre-signed list via the /v1/pki/issue/sap-oracle endpoint in a tight loop with connection reuse, or move issuance to the Express backend where a single HTTPS connection to Vault can issue all 150 sequentially over one kept-alive connection (no TCP/TLS setup per cert). The backend's axios client already uses connection pooling — the certificate-replacement operation should be server-side, not SSH-then-curl.

Potential saving: reduces 150 TCP handshakes + 150 TLS sessions to 1 TCP + 1 TLS. At ~50 ms round-trip per curl call, this also cuts the demo "Deploy Vault Certificates" wall-clock time from ~7.5 s to <1 s.
Evidence: scripts/replace-with-vault-certificates.sh:81–85 — curl per cert · routes/vault.js:10 — vaultClient singleton with connection pooling already in place
🟡 Low-medium impact — Algorithmic redundancy
Skip Next.js rebuild on re-run of setup.sh if source is unchanged
npm run build at setup.sh:326 runs unconditionally on every re-run, even if the source code has not changed. A Next.js build on RHEL Power takes 60–120 s and involves many file I/O operations. Adding a guard — check for .next/BUILD_ID and a source hash, or simply ask — would eliminate this on idempotent re-runs (e.g. restart-after-reboot scenarios).

This is more a developer-ergonomics win than a significant energy saving, but it removes unnecessary repeated work.
Evidence: scripts/setup.sh:322–327 — unconditional `npm run build`
🟡 Low impact — Logging overhead
Gate startup env-var logging behind DEBUG or NODE_ENV=development
server/index.js:56-58 logs AIX_HOST, VAULT_ADDR, and POWERSC_URL on every process start, unconditionally. For a demo server that may restart multiple times, this is minor — but it also logs the absence of POWERSC_PASS in a visible way. Gating behind if (process.env.NODE_ENV !== 'production') is the pattern.

Note: this is very low impact for a demo. Flag as a recipe hygiene point rather than an energy concern.
Evidence: server/index.js:56-58 — unconditional console.log on start
🟢 Minor — Shell script efficiency
Share a single openssl config template across all 150 cert generations
generate-old-certificates.sh:83-95 writes a fresh .cnf file per certificate — 150 file writes and 150 unlinks. The config is identical for all certs except CN=. Using a single template with -subj "/CN=$cn/O=Demo..." inline on the openssl command line eliminates the per-cert file I/O entirely. This is a clean-code improvement as much as an energy one.
Evidence: generate-old-certificates.sh:83-95 — cat to $cfg, rm -f $cfg per cert
✅ Positive patterns — already well done
Pre-built Power-native container · Idempotent guards · Streaming SSH output · Singleton Axios client
Pre-built ICR image: icr.io/ppc64le-oss/vault-ppc64le:v1.14.8 eliminates compile-from-source energy cost. Contrast with building llama.cpp from source (10–15 minute build each deploy). ✓

Idempotent setup guards: Podman check, Node version gate, .env.local existence check, and PKI "already mounted" 400-skip all prevent redundant work on re-runs. ✓

Streaming SSH output: ssh.js processes stdout as a stream with a line buffer — it does not accumulate the full script output in memory before acting. For 150-cert operations this avoids a potentially large string allocation. ✓

Axios singleton: vaultClient in vault.js is instantiated once at module load — connection pooling is reused across requests. ✓

PassportEye principle applied correctly: certificate issuance uses Vault's PKI engine (a deterministic cryptographic service), not an LLM. The right tool for the job — no AI inference in the cert path at all. ✓
🔵 Future / Recipe evolution
Consider moving certificate replacement fully server-side to leverage the Axios connection pool
The current architecture for "Deploy Vault Certificates" is: Express backend → SSH to AIX → curl from AIX to Vault. This means AIX is making 150 outbound HTTPS calls to Vault, each with its own TCP/TLS setup.

An alternative: Express backend issues all 150 certs via the vaultClient Axios pool (one connection, 150 requests), then transfers the cert/key PEM content over SSH in a single SFTP batch. This would be faster, more reliable, and remove the VAULT_ADDR / VAULT_ADDR_EXTERNAL split complexity.

This is a meaningful architecture change — not suggested for the current sprint, but the right direction for a production-hardened version of this recipe.
